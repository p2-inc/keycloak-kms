# Native mode — keys that never leave the KMS

> **Experimental in this release.** Envelope mode is the supported default. The mechanism below has
> no production mileage, and the mode has a throughput ceiling envelope mode does not.

In envelope mode the private key is decrypted into process memory and signatures are computed
locally — the same exposure as vanilla Keycloak while running, and strictly better at rest. For
most people that closes the finding.

Native mode is for the realm whose contract says the signing key must never exist in plaintext
outside a hardware security module. The key is generated by AWS inside an asymmetric CMK, is not
extractable by anyone including us, and every token issuance is one `kms:Sign`.

## How it works without forking Keycloak

Keycloak's `AsymmetricSignatureSignerContext.sign()` does exactly this:

```java
Signature signature = Signature.getInstance(JavaAlgorithm.getJavaAlgorithm(alg, curve));
signature.initSign((PrivateKey) key.getPrivateKey());
signature.update(data);
return signature.sign();
```

No provider is named. The JDK therefore defers provider selection until `initSign(key)` and picks
the first registered provider that accepts that key. `KeyWrapper.setPrivateKey` takes any
`java.security.Key`, so the extension hands it a `KmsPrivateKey` — an opaque object with
`getFormat()` and `getEncoded()` returning null, because there genuinely is nothing to encode.

SunEC and SunRsaSign both advertise `SupportedKeyClasses`, so the JDK skips them for a key that
implements neither `ECPrivateKey` nor `RSAPrivateKey`, and reaches `KmsJcaProvider` instead. That
provider is registered **last** and accepts nothing but a `KmsPrivateKey`, so every ordinary key in
the process — other realms, TLS, everything — continues to use the JDK's own providers. There is a
test that asserts precisely that.

## Setting one up

EC first. Inside KMS an ECDSA signature is faster and cheaper than an RSA one, ES256 is understood
by every relying party that matters, and EC avoids the PSS parameter negotiation RSA needs.

```bash
aws kms create-key \
  --key-usage SIGN_VERIFY \
  --key-spec ECC_NIST_P256 \
  --description "Keycloak signing key — customer-b"
```

Grant the Keycloak role `kms:Sign`, `kms:GetPublicKey` and `kms:DescribeKey` on that ARN, then add
a `kms-ec-native` provider to the realm with `kmsKeyId` set to it and `algorithm` set to `ES256`.
Set the realm's default signature algorithm to `ES256` so the key is actually chosen.

The extension calls `kms:GetPublicKey`, derives the kid from it exactly as any other Keycloak key,
caches the public key in config so JWKS costs no KMS call, and validates that the key is asymmetric,
enabled and of the right spec before saving anything.

`kms-rsa-native` works the same way for realms whose clients cannot do ES256, and additionally
mints a self-signed certificate (SAML descriptors read it) by signing the to-be-signed structure
through `kms:Sign` — a certificate does not need the private key in hand, only a signature over it.

## What it costs

Said out loud at provider creation, because these are the facts discovered too late:

```
WARN  kms: realm 'customer-b': native provider added (kid t1pZvt…)
      key=arn:aws:kms:us-east-1:111122223333:key/9c4e… (ECC_NIST_P256, SIGN_VERIFY, enabled)
      *** NATIVE MODE IS EXPERIMENTAL IN THIS RELEASE. Envelope mode is the supported default. ***
      This CMK bills for as long as it exists — this extension will never delete it.
      Every token this realm issues costs one kms:Sign call and adds single-digit to low-tens of
      milliseconds to the token endpoint.
      kms:Sign draws on a per-region asymmetric-operation quota shared by your whole AWS account.
      Check Service Quotas before pointing a high-volume realm at this mode.
```

- **One CMK per realm key**, about $1/month each, forever. Ten realms is ten dollars; five hundred
  is five hundred.
- **Per-signature charges**, small individually.
- **An account-wide quota** on asymmetric operations. This is the real constraint: it is a ceiling
  on how fast the whole cluster can issue tokens for native realms, and it is shared with anything
  else in the account doing asymmetric KMS work. Check Service Quotas for your region.

Native mode is a per-realm option, not a cluster-wide posture. One realm out of forty is the
expected ratio.

## Bring your own key

The extension **never creates and never deletes** asymmetric CMKs. There is no option to make it.

The plan allowed for an opt-in auto-create flag; it was dropped during implementation because it
could not be made safe enough to be worth having. An asymmetric CMK bills for as long as it exists,
so implicit creation orphans a billable key every time someone deletes a realm — and the obvious
fix, deleting the key with the realm, means an automated system scheduling the destruction of
something that may still be signing production tokens. Creating the key with one `aws kms
create-key` is not the hard part of adopting this mode.

## Migration cannot target native mode, by design

AWS KMS can import asymmetric key material, but it is a multi-step wrapping ceremony and imported
material cannot be automatically rotated.

More to the point it is the wrong thing to want. Native mode's value is that the private key has
*never* existed outside the HSM. Importing a key that spent years in a Postgres table keeps every
cost of native mode and throws away the only property it buys.

So the path is the two-step one:

1. Migrate to envelope mode — zero downtime, same kid.
2. Rotate to a native provider — a new kid under standard passive-key semantics, and material that
   has never touched the database.

## Known divergence: PSS against LocalStack

AWS documents a PSS salt length equal to the digest length. **LocalStack signs with the maximum
salt length instead.** Both are well-formed PSS and both verify, but a strict JOSE verifier expects
the AWS convention.

The practical consequence is development-only: a `PS*` realm key against LocalStack produces tokens
whose signatures some verifiers reject. Against real AWS the salt length is the one relying parties
expect. `AwsKmsProviderIT` records which of the two appeared rather than pretending the difference
is not there.

ES256 does not have this problem, which is one more reason it leads.

## Limits

- **No EdDSA.** AWS KMS has no Ed25519 key spec, so this can never be native. Envelope mode could
  support it and does not yet.
- **Verification is never routed through the KMS.** Keycloak verifies with the public key locally,
  which is faster, free, and no less secure — a public key is public.
- **No certificate for EC by default**, matching stock ECDSA providers, which make it optional.
