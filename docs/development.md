# Development

## Build and test

```bash
mvn package -DskipTests   # the jar, in target/keycloak-kms.jar
mvn test                  # unit tests only — fast, no Docker
mvn verify                # everything, including the integration suites — needs Docker
mvn com.spotify.fmt:fmt-maven-plugin:format   # Google Java style; CI checks it
```

Java 21. Keycloak 26.7.3.

## The dev environment

```bash
make dev      # build the jar, start Keycloak + LocalStack, foreground
make start    # the same, detached
make logs     # follow Keycloak
make clean    # stop, drop volumes, mvn clean
```

Nothing talks to AWS. LocalStack provides KMS and creates three CMKs at startup:
`alias/keycloak-realm-keys` (symmetric, for envelope mode), `alias/keycloak-native-ec` and
`alias/keycloak-native-rsa`.

Two realms are imported:

- **`dev`** — no key providers of its own, so Keycloak creates its stock ones with plaintext
  material in the database. This is the realm to migrate.
- **`native`** — empty, with `defaultSignatureAlgorithm: ES256`. Add a `kms-ec-native` provider
  with `kmsKeyId=alias/keycloak-native-ec` to try sign-in-KMS.

Both have a public client `app` with direct grants and a user `testuser` / `password`.

```
Admin console : http://localhost:8080/admin   (admin / admin)
LocalStack    : http://localhost:4566
```

### Watching a migration

```bash
./docker/migrate-dev.sh
```

Prints the realm's key status and JWKS before and after, runs the migration, and diffs the kid
lists. Identical kid lists are the point.

## Test layers

| Suite | Needs | What it is for |
|---|---|---|
| `*Test` (surefire) | nothing | Everything provable in isolation: the codec, the local backend, SigV4, the credential chain, the key providers, the migrator, native routing. ~160 tests, a few seconds. |
| `AwsKmsProviderIT` | Docker | The AWS backend against LocalStack's real KMS API. Proves the properties AWS enforces rather than we do. |
| `KeycloakKmsIT` | Docker | The extension inside a real Keycloak 26.7.3: providers register, realms sign real tokens, migration preserves JWKS, native EC issues ES256. |

### Things worth knowing before you add a test

**Drive off Keycloak's own constants, not your memory of them.** The native routing tests derive
the JCA algorithm name from `JavaAlgorithm.getJavaAlgorithm(...)` rather than hard-coding it. That
is not fastidiousness: an earlier version hard-coded `"RSASSA-PSS"`, whereas Keycloak actually maps
PS256 to `"SHA256withRSAandMGF1"`, and the tests passed while PSS realm keys would have found no
provider at all.

**The admin components API is not a view of stored config.** Keycloak builds the representation
from the properties a factory declares, so generated values — the kid, the wrapped material — are
simply absent. Asserting `privateKey == null` against it passes whether or not the plaintext is
really gone. Assert through `GET /realms/{realm}/kms/status`, which reads the model.

**SigV4 vectors come from botocore**, not from us. `src/test/resources/sigv4-vectors.json` is
generated by `regenerate-sigv4-vectors.sh` using the botocore bundled with the AWS CLI. If a
signature test fails, the answer is almost never to regenerate the vectors — that would delete the
test. Regenerate only when adding a new request shape.

**LocalStack diverges from AWS on PSS salt length.** See [native-mode.md](native-mode.md#known-divergence-pss-against-localstack).

## Layout

```
spi/         the kms SPI: KmsProvider, EncryptionContext, KmsSigningAlgorithm
aws/         AwsKmsProvider, KmsApi (the wire protocol), AwsSigV4Signer
aws/credentials/   the six credential sources and the chain
local/       LocalKmsProvider — AES-GCM under a local KEK, for dev and tests
keys/        KeyCache, WrappedMaterial (the kms://v1/ codec), KmsKeyType
keys/envelope/     the four envelope providers
keys/nativemode/   KmsPrivateKey, KmsJcaProvider, KmsSignatureSpi, SelfSignedCertMinter
migration/   KmsKeyMigrator, LegacyKeyReader
resource/    the REST resource at /realms/{realm}/kms
bootstrap/   new-realm installer, startup sweep
```

## Conventions

Phase Two house style, the same as the other extensions:

- `@AutoService` for SPI registration, so there are no hand-maintained `META-INF/services` files
- `@JBossLog` (Lombok) for logging
- `representation` for JAX-RS DTOs
- Every Keycloak dependency `provided`; **no runtime dependencies at all**, which is why AWS is
  reached with hand-rolled SigV4 over the JDK HTTP client rather than the AWS SDK
- Google Java Format, checked in CI
